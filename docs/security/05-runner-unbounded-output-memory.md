# ODY-005: 러너 stdout/stderr 무제한 메모리 수집

## 취약점 요약

- **심각도:** 높음
- **영향:** runner 컨테이너 OOM, 동시에 실행 중인 다른 응시 작업 종료, 서비스 거부
- **원인:** 자식 프로세스 출력을 `subprocess.communicate()`로 끝까지 메모리에 모은 후에야 잘라낸다.
- **주요 근거:** `apps/runner/sandbox.py:121`, `apps/runner/sandbox.py:137`, `apps/runner/sandbox.py:152`

## 상세

응시자 명령의 stdout과 stderr는 PIPE로 연결되며 `communicate()`가 프로세스 종료까지 모든 바이트를 메모리에 축적한다. 이후 `_decode()` 단계에서 반환 크기를 제한하더라도 이미 메모리는 소비된 뒤다.

Compose의 컨테이너 메모리 제한은 피해 범위를 호스트 전체에서 runner 컨테이너로 줄일 뿐이다. runner 컨테이너에는 여러 응시자의 작업과 큐 소비 스레드가 함께 있으므로 한 응시자의 출력 폭주가 다른 응시자의 실행을 중단시킬 수 있다.

## 재현 방법(공격 방법)

전용 테스트 runner에서 작은 출력부터 점진적으로 확인한다. 운영 기본 메모리 한계까지 출력하지 않는다.

```bash
python3 - <<'PY'
import sys
for _ in range(64):
    sys.stdout.write("A" * 1024 * 1024)
PY
```

명령 실행 중 `docker stats`로 runner 메모리가 출력량에 비례해 증가하는지 확인한다. 검증 즉시 작업을 종료하고 테스트 스택을 재시작한다.

## 공격 예시

1. **stdout 폭주:** 무한 루프에서 큰 문자열을 계속 출력해 컨테이너 메모리를 채운다.
2. **stderr 폭주:** 진단 메시지를 stderr로 대량 출력하여 작은 최종 stderr 제한을 우회해 수집 단계 메모리를 고갈시킨다.
3. **다중 자식 출력:** 여러 자식 프로세스가 같은 파이프에 동시에 출력해 제한 시간 안에 더 빠르게 메모리를 소모한다.
4. **압축 해제 출력:** 작은 입력에서 매우 큰 텍스트를 생성하는 프로그램을 실행해 명령 길이 제한과 파일 크기 제한을 우회한다.

## 해결 방법

1. stdout/stderr를 비동기 또는 별도 스레드로 스트리밍하면서 각각의 바이트 상한까지만 보존한다.
2. 상한을 넘으면 파이프를 계속 drain하되 데이터를 버리거나 프로세스를 즉시 종료한다.
3. 실행별 cgroup 메모리와 I/O 한도를 두어 한 작업이 runner 전체 한도를 공유하지 않게 한다.
4. 출력 속도 제한과 최대 총 출력량을 설정하고 결과에 `truncated=true`를 명시한다.
5. OOM 종료를 감지해 해당 execution만 실패 처리하고 다른 작업을 재시도할 수 있게 runner 프로세스와 실행 프로세스를 별도 컨테이너로 분리한다.
